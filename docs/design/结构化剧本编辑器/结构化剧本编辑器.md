# 结构化剧本编辑器设计

> - **范围**：短剧工作室「剧本」页的单集剧本从 Markdown 文本改为结构化存储（场次 + 元素行级表），配套元素化编辑器、剧本人物表与地点表、场次信息与集统计、原著对照分栏。不含：A（剧本提示词手艺补充）、B（跨集状态提取）、C（写后内容审查），这三项在本项目之后各自单独设计。
> - **日期 / 状态**：2026-11-21 · 设计待确认。分支 `feat/structured-script-editor`。
> - **方案演进**：存储选行级表、人物身份选剧本自带人物表、整集重写选智能匹配保留，三项均为用户选定；之后用户提出拆解直接用剧本结构里的人物、地点，不再重新提取，造型与描述保留一次轻量模型补充（§7.6，第⑤步）；曾提议「大纲阶段先出人物表」，用户澄清本意后撤回；审阅后补了道具 / 不说话人物字段、锁定集冻结 `script_md`、整部剧转换、人物确认状态。
> - **需求来源**：用户在调研 [looplj/reveric](https://github.com/looplj/reveric) 后提出：「改对白时格式容易乱，想要结构化存储，而且（编辑器）过于单薄」。单薄指四项：元素化编辑手感、角色与场次绑定、场次级信息与状态、原著对照分栏（用户在选项中勾选）。
> - **证据约定**：**事实**附文件路径或来源链接；**推断**是基于事实的判断；**提案**是尚未实现的设计；**默认值**是用户没被问到、由本文暂定的做法，实现前可推翻。标「我方决定」的是设计者替用户做的取舍。
> - **配套演示**：[结构化剧本编辑器-演示.html](结构化剧本编辑器-演示.html)（方案讲解 + 解析 / 合并交互演示 + 数据与接口）；[结构化剧本编辑器-原型.html](结构化剧本编辑器-原型.html)（高保真编辑器原型）。
> - **许可边界**：Reveric 为 AGPL-3.0（另有 CLA），本仓库为 MIT。本设计只借鉴其「剧本由类型化元素组成、对白必须挂在角色行后」的思路，不复制其代码、提示词或文案。实现时不得打开 Reveric 源码照抄。

## 1. 设计摘要

- **问题**：剧本正文是一整段 Markdown（`drama_episodes.script_md`），用通用 Tiptap Markdown 编辑。对白、人物名、括号提示全靠手打符号，改几下就乱；场次目录靠正则从标题猜；人物和地点只是字符串，改名、统计、跨集查询都做不了。
- **目标**：
  1. 剧本以「场次 → 元素」结构存储，格式由数据保证，不再靠用户手打符号。
  2. 编辑手感像专业剧本软件：Enter 自动接下一种元素，对白自动挂到说话人。
  3. 人物、地点有身份（ID），改名一处生效，后续能接资产、跨集状态提取（B）和审查（C）。
  4. 现有流水线（拆解、分镜、上集衔接、Agent 改剧本）不因本次改造而回归。
- **推荐结论**（用户已选）：
  - **行级表**（用户选方案 1）：新增 `drama_scenes`、`drama_script_elements`，一个元素一行。
  - **剧本自带人物表和地点表**（用户选方案 1）：`drama_script_characters`、`drama_script_locations`，元素引用其 ID；资产拆解后回填画布节点 ID。
  - **`script_md` 保留为派生列**（我方决定）：结构是唯一真源，每次写结构时在同一事务里渲染出 `script_md`，所以读 `script_md` 的 7 处下游本期不用改。
  - **五步交付**：①数据模型、解析渲染、存量转换；②元素化编辑器 + 人物绑定；③场次信息与集统计；④原著对照分栏；⑤资产拆解直接按人物表、地点表和剧本结构建资产，模型只补造型、外貌和音色（用户选定）。

### 2.2 设计约束

1. 写剧本时角色卡和场景资产大多**还不存在**（拆解在剧本之后），所以人物、地点身份不能依赖画布节点，这是人物表的由来。
2. 已锁定集的剧本只读，这条规则不变。
3. 模型输出（含用户自定义提示词的输出）是自由文本，必须能解析成结构；解析不了的部分不能丢。
4. 开发环境迁移会被热执行，改已执行的迁移会导致 checksum 报错（见团队记忆）；迁移一次写对，数据转换不放在 SQL 里。
5. Go 函数 ≤ 80 行、≤ 50 条语句、认知复杂度 ≤ 20（`AGENTS.md`）。
6. 先写失败测试；后端测试放 `backend/internal/tests/`，前端放 `web/src/tests/`。

## 3. 用户与场景

- **用户**：做 AI 短剧的个人创作者，手上有模型生成或导入的分集剧本，要在拆解资产前改顺。
- **场景**：
  1. 模型生成了第 3 集，用户要改几句对白、插一句括号提示、删一场。
  2. 用户发现「林川」该叫「林骁」，希望全剧一次改完。
  3. 用户对照原著第 12 章，检查这一集有没有漏掉关键对白。
  4. 用户想一眼看出这一集几场、多长、是否超出单集时长。
- **成功标准**：
  - 改对白时不需要输入任何格式符号（`△`、`：`、括号）。
  - 任何编辑都不可能产出「没有说话人的对白」。
  - 现有全部短剧剧本转换后，渲染出的 `script_md` 与原文在语义上一致（场次、说话人、台词、动作不丢）。

## 4. 方案

### 4.1 考虑过的做法

| 方案 | 做法 | 取舍 | 结论 |
| --- | --- | --- | --- |
| 1. 行级表 | 新表存场次和元素，一个元素一行 | 能按人物、场次查询，元素 ID 稳定，可被 B/C 和以后的分镜引用；迁移和保存逻辑最重 | **用户选定** |
| 2. 整集一个 JSON 列 | `script_json` 存场次数组 | 改动最小，沿用集级锁；不能用 SQL 跨集查人物，元素没有全局 ID | 未选 |
| 3. Markdown 仍为真源，编辑器加约束 | 只改前端 | 不是结构化存储，格式混乱的根因还在 | 排除 |

人物身份的三种做法：剧本自带人物表（**用户选定**）、只存名字待拆解后关联（改名不联动，错字变两人）、拆解前禁止编辑（违背现流程，排除）。

### 4.2 设计原则

1. **结构是唯一真源**，`script_md` 只是渲染结果，任何写入都先变成结构。
2. **一个解析器、一个渲染器**，都在 Go 里；前端不重复实现解析（我方决定，避免两套规则漂移）。
3. **不丢内容**：解析不出来的行降级为「动作」并标警告，绝不丢弃。
4. **集级 revision 不变**：一集的所有场次和元素共用这一集的 `revision`，保存是整集一次事务。

## 5. 数据模型（提案）

迁移编号取实现时最新（当前应为 `0045`）。所有表带 `user_id` 并按它隔离。

### 5.1 `drama_script_characters`（剧本人物表）

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `user_id`、`drama_id` | 归属 |
| `name` | 正式名；同一短剧内忽略大小写和首尾空白唯一 |
| `aliases` | jsonb 字符串数组；改名时旧名自动进别名 |
| `note` | 一句话备注（身份 / 声线），可空 |
| `canvas_node_id` | 拆解后回填的画布角色节点 ID，可空 |
| `confirmed` | bool；解析时自动登记的为 false，用户在人物表里点「确认」或编辑过该人物后为 true；用户手动新建的直接为 true |
| `position` | 列表排序 |

### 5.2 `drama_script_locations`（地点表）

同人物表的 `id / user_id / drama_id / name / aliases / canvas_node_id / confirmed / position`，`canvas_node_id` 回填场景节点。

### 5.3 `drama_scenes`

| 字段 | 说明 |
| --- | --- |
| `id`、`user_id`、`drama_id`、`episode_id` | 归属 |
| `position` | 集内顺序，从 0 起；场号显示为「集号-(position+1)」，不单独存 |
| `int_ext` | `interior` / `exterior` / `interior_exterior` / 空 |
| `time_label` | 日 / 夜，或自由文本（清晨、黄昏）；可空 |
| `location_id` | 引用地点表，可空 |
| `title` | 场次短标题（如「码头对峙」），可空 |
| `summary` | 场次梗概，可空 |
| `emotions` | jsonb 字符串数组，情绪标签 |
| `extra_character_ids` | jsonb，本场出场但不说话的人物（引用人物表）；渲染「人物：」行时与本场说话人合并 |
| `props` | jsonb 字符串数组，对应「道具：…」行，原样渲染 |

### 5.4 `drama_script_elements`

| 字段 | 说明 |
| --- | --- |
| `id`、`user_id`、`drama_id`、`episode_id`、`scene_id` | 归属 |
| `position` | 场内顺序 |
| `type` | 见下表 |
| `text` | 正文；`character` 类型必须为空 |
| `character_id` | 仅 `character` 类型必填，引用人物表 |
| `extension` | 仅 `character` 类型：空 / `OS` / `VO` |

元素类型（我方决定：在 Reveric 的类型集合基础上，补上现有格式里的闪回和空镜，保证现有剧本能无损转换）：

| type | 含义 | 现有格式对应 |
| --- | --- | --- |
| `action` | 动作与画面 | `△ …` |
| `character` | 说话人 | `人物名`、`人物名（OS）` 的人物部分 |
| `parenthetical` | 语气 / 同时动作 | `人物名（压低声音）：` 的括号部分 |
| `dialogue` | 台词 | 冒号后的台词 |
| `transition` | 转场 | 如「切至」「淡出」 |
| `subtitle` | 字幕 | `【字幕：…】` |
| `shot` | 空镜 | `【空镜】…` |
| `flashback_start` / `flashback_end` | 闪回起止 | `【闪回】` / `【闪回结束】` |
| `note` | 作者备注，不进入拍摄 | 无（新增） |

场内顺序约束（保存时服务端校验，前端编辑时提前拦截）：

- `parenthetical` 和 `dialogue` 前面必须是同一说话块：紧挨着的前一个元素是 `character`、`parenthetical` 或 `dialogue`，且往前能找到 `character`。
- `character` 后面至少跟一个 `dialogue`（允许中间夹 `parenthetical`）；`parenthetical` 后面也必须跟 `dialogue`，否则渲染时括号会丢（实现时补的规则）。
- `flashback_start` 与 `flashback_end` 在同一场内成对，不嵌套。
- 违反 → 新错误码 67043「剧本结构不合法」，响应里带出第几场第几个元素。

场次标题下的「人物：…」「道具：…」行（我方决定，保证拆解读到的内容不变）：「人物：」里没说话的人存进 `extra_character_ids`，渲染时把本场说话人和它们按首次出现顺序合并输出；「道具：」存进 `props`，原样渲染。道具本期不建表。

### 5.5 `drama_episodes` / `drama_projects` 的变化

- `script_md` 保留，变成派生列：任何结构写入都在同一事务里重新渲染。
- `drama_projects` 新增 `script_structured bool`（默认 false），表示这部剧已整部转成结构（见 §7.3）。
- **已锁定集的 `script_md` 冻结**（我方决定）：锁定集的结构仍可随人物改名显示新名，但 `script_md` 不再重渲染，保持锁定那一刻的文本。拆解、分镜按锁定时的文本和资产名对得上，改名不会让分镜里的 `@资产名` 失配。

### 5.6 人物表、地点表从哪来

- **解析剧本时自动登记**（我方决定）：模型产出的剧本解析出新说话人或新地点时，按名字和别名在表里查；查不到就新建，并标为「本次新增」，前端人物表里高亮提示用户确认。
- **资产拆解直接用这两张表建资产**（第⑤步，见 §7.6）：不再让模型从剧本里重新提取人物和地点，拆解建出的角色卡、场景节点 ID 回填到 `canvas_node_id`。第⑤步上线前，过渡做法是拆解照旧，写完画布后按名字和别名回填 `canvas_node_id`，对不上的保持为空、不报错。
- `characters_md`（人物小传）保持自由文本，不解析进人物表（推断：它是散文体，解析不可靠）。
  - 2026-11-26 修订：人物小传以人物表的 `note` 为准。研读生成的 `characters_md` 按「- **名字／别名**：小传」「标题 + 字段」两种写法惰性拆进人物表（不覆盖已有小传），之后写分集剧本、拆解、资产图提示词、分镜读到的 `characters_md` 都由人物表拼出，没有已确认人物时退回原传记。
  - 地点表同样有描述（`note`）：拆解、资产图提示词、分镜的 `locations_md` 由地点表拼出，只列写了描述的地点；与剧本冲突时以剧本为准。

## 6. 接口（提案）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/dramas/:id/episodes/:no/script` | 返回这一集的结构：`revision`、`locked`、`scenes[]`（每个带 `elements[]`）；未转换的集在这里惰性转换 |
| PUT | `/dramas/:id/episodes/:no/script` | 整集保存：`revision` + `scenes[]`。元素和场次带 `id` 表示已有，`id` 为空表示新增，请求里没出现的视为删除。服务端在一个事务里比对后增改删、渲染 `script_md`、`revision+1`。响应按提交顺序返回所有场次和元素的新 `id`，前端据此关联新行 |
| POST | `/dramas/:id/script/parse` | 把一段纯文本解析成场次 / 元素，供粘贴使用，**不保存剧本**；文本里新出现的人物、地点会登记进表并标为「待确认」，所以响应里的 ID 都是真实可用的（实现时的简化：设计初稿是只标出不建表，那样前端要先建人物再回填 ID，多一轮往返） |
| GET | `/dramas/:id/script-characters` | 人物表，带每人出现的集号和台词条数（实时统计） |
| POST / PATCH / DELETE | `/dramas/:id/script-characters[/:cid]` | 增改删人物；改名时旧名进别名；仍被元素引用的人物删除 → 新错误码 67044，响应带引用的集号 |
| GET / POST / PATCH / DELETE | `/dramas/:id/script-locations[/:lid]` | 地点表，规则同上（删除仍被引用的地点 → 67044） |

- `PATCH /dramas/:id/episodes/:no` 的 HTTP 入口不再接受 `script_md`，带了返回 400（10001）（我方决定）：用户剧本只能走结构接口，避免绕过校验。请求结构体里该字段仍保留（带 json 标签），因为 Agent 审批把整个请求序列化进审批记录、批准后再反序列化。注意 Agent 审批执行（`service/agent/drama_approval.go` 的 `executeDramaEpisode`）也调用同一个 `UpdateEpisode` 服务，要改成走「解析 → 写结构」的服务方法；它的防重复判定 `sameDramaText(req.ScriptMD, ep.ScriptMD)` 在解析再渲染后会失效。**实现方式**：Agent 提议修改剧本时，服务新增 `PreviewScript`（按当前人物表解析并渲染，不写库，新名字只在内存里分临时 ID），审批记录里存的和给用户看的都是这份渲染后的文本；批准后再解析它得到同样的 `script_md`，原判定照常成立，不用改。
- 锁定集：`PUT …/script` 返回 67005；人物表、地点表的改名**仍允许**，只重渲染未锁定集的 `script_md`（锁定集冻结，见 §5.5）。
- 改名、删除前，这部剧必须已整部转换（见 §7.3），所以引用检查和改名能覆盖全部集。
- 改名重渲染的集 `revision+1`，并逐集推送集更新通知；当前打开的编辑器由发起改名的页面自己重新读取，不弹冲突。
- 人物或地点改名不同步画布节点名（默认值）：两边靠 `canvas_node_id` 关联，画布节点名由用户在资产管理里自行修改。

## 7. 解析、渲染与转换（提案）

### 7.1 解析器（Go，`internal/drama/script` 一类的新包）

- 输入纯文本 + 当前人物表、地点表，输出场次 / 元素数组 + 警告列表 + 新人物 / 新地点列表。
- 按 §2.1 的内置格式识别；容忍常见变体：Markdown 标题包着的场次标题、整行加粗、`INT.`/`EXT.`、半角冒号和括号、`第N集` 行（丢弃，集号以所在集为准）。
- **文头不识别台词**（用真实剧本试用后补的规则）：文本里有场次标题时，第一个标题之前的内容是文头（剧名、时代背景、人物介绍这类「字段名：内容」），只认方括号标注和 `△`，其余原样作为动作保存，不当台词、不登记人物；文本里完全没有场次标题时（粘贴来的几行对白）才是片段，照常识别台词。
- **字段名永远不是说话人**：「剧名、时代背景、核心视觉基调、主要人物、场景、地点、时间、备注、说明」等一份固定的字段名清单，即使出现在场次里也按动作保存，不登记人物。
- 认不出的非空行 → `action` + 警告，原文不丢。
- 场次标题之前的内容 → 自动放进第一场（无地点），并给出警告。

### 7.2 渲染器

- 结构 → 内置格式文本，与 `scripts_draft.md` 规定的格式一致；`note` 不渲染进 `script_md`（我方决定：备注不该被拆解和分镜读到）。
- 性质：`render(parse(render(x))) == render(x)`，作为测试断言。

### 7.3 写入路径怎么改

| 路径 | 改法 |
| --- | --- |
| 用户编辑 | 走 `PUT …/script` |
| 分集剧本任务 `saveDramaScript` | 模型输出 → 解析 → 写结构 → 渲染 `script_md`，同一事务 |
| 规划时已分集剧本、大纲输出带 `script_md` | 同上 |
| Agent `drama_update_episode` 的 `script_md` | 入参不变，审批通过后解析成结构再写；工具描述补一句「会按标准剧本格式解析」 |
| 存量剧 | **按整部剧惰性转换**（我方决定）：任何结构读写、人物表 / 地点表操作、或流水线写剧本时，发现这部剧 `script_structured=false`，就在一个事务里把全部集解析并落库，再置为 true。未锁定集的 `script_md` 换成渲染结果，**两类集的 `revision` 都不变**（实现时的修正：初稿写的是未锁定集 +1，但前端手里的集摘要还是旧 revision，转换后用户改标题、钩子会白白撞一次 409；格式归一不是用户可见的内容变化）；**锁定集只建结构，`script_md` 原样保留** |

### 7.4 整集重写时保留已有信息（用户选方案 1）

重新生成剧本、Agent 改剧本、多行粘贴覆盖整集时，都是「新文本 → 解析 → 与旧结构合并」，而不是整集替换：

1. **场次对齐**：以「内 / 外 + 时间 + 地点 ID」为键（地点别名命中也算同一地点），新剧本的每一场依次找第一个还没被配对、键相同的旧场次，不要求顺序一致（我方决定：调换场次顺序时梗概不丢；同一地点出现多次时按出现先后配对）。对上的场次沿用原场次 ID，并保留短标题、梗概、情绪；对不上的新场次这三项为空。
2. **元素对齐**：对上的场次内，元素按 (类型, 说话人 ID, 文本) 做最长公共子序列比对；完全相同的沿用原元素 ID。类型和说话人相同、只改了文本的，在相邻的未匹配区间内按顺序配对，也沿用原 ID（视为「修改」）。
3. **备注保留**：`note` 不在新文本里，按它原来紧挨着的前一个元素定位，前一个元素还在就插到它后面；前一个元素被删了，就挂到同场里离它最近的、仍然保留的元素之后；整场都被删了，就放到新剧本第一场开头，并标警告「N 条备注的原位置已删除」。插入点后面紧跟括号或对白时，往后挪到这段说话结束，不能夹在角色行和对白之间（否则违反 §5.4 的顺序约束）。
4. 对不上的旧场次和旧元素删除。
5. 合并结果返回「保留 / 修改 / 新增 / 删除」的条数，写入结果提示与 Agent 审批预览都用它。

`extra_character_ids`、`props` 以新文本为准（它们会渲染进文本，Agent 看得到）。

Agent 审批预览显示「解析 + 合并 + 渲染」之后的文本，与实际落库内容一致（我方决定）。

### 7.5 转换策略的理由

按整部剧而不是按集转换，理由：人物表是整部剧共享的，只转一集会让改名、删除的引用检查漏掉没转的集。不做一次性回填，理由：迁移不能写 Go 逻辑，单独回填命令又要运维执行。转换由打开剧本页触发，在编辑器载入前完成。转换不升 `revision`，所以不会让编辑器、挂起中的 Agent 审批报冲突。

**「语义一致」的验收口径**（我方决定，可自动断言）：把转换前文本和渲染结果各自解析成「(场次标题, 元素类型, 说话人, 文本)」序列，两者逐项相等；空白、全半角标点差异不计。用仓库开发库里现有短剧剧本全部跑一遍，作为第①步的验收。

### 7.6 资产拆解改为按结构建资产（第⑤步）

**来由**：用户指出，剧本解析成结构后，人物、地点、道具和出现集数都已经有了，后面的拆解不该再让模型读一遍剧本重新提取，「否则就对不上了」。造型、外貌、音色这些结构里没有的信息，用户选**保留一次轻量模型调用、只能给已有人物补充**（方案 1）；另两个方案（完全不调模型、剧本角色行可选造型）未选。

**确定性部分（不调模型）**，对所选集：

| 资产 | 来源 | 规则 |
| --- | --- | --- |
| 角色卡 + 角色节点 | 人物表中在所选集里有角色行或在 `extra_character_ids` 里的人 | 已有 `canvas_node_id` 的复用并补集数；没有的新建，节点 `data.drama` 写正式名、别名，回填 `canvas_node_id` |
| 场景节点 | 地点表中被所选集场次引用的地点 | 同上 |
| 道具节点 | 所选集各场 `props` | 按名字去重，与画布已有道具节点按名字 / 别名合并；道具不建表 |
| 出现集数 | 剧本结构统计 | 与节点已有集数取并集 |

画布节点的 `data.drama` 新增 `script_character_id` / `script_location_id`（我方决定），让一个人的多个造型节点都能认回同一个人物；人物表的 `canvas_node_id` 指向这个人的**主造型节点**（第一个建出的），用作头像。

**模型部分（补充，不新建身份）**，每批一次调用：

- 输入：本批涉及的人物（ID、正式名、别名、备注、画布上已有的造型）、地点、道具名，以及本批各集 `script_md`。
- 输出：人物的造型列表（造型名、出现集号、外貌描述）和音色描述；地点、道具的外貌描述。
- 校验：输出里只能引用输入给出的 ID；出现未知 ID 或新名字的条目丢弃并记警告，不失败。同一人多个造型 → 每个造型一个角色节点（沿用现在 `data.drama.look` 的做法）。
- 先建确定性资产，再做模型补充：模型调用失败时，资产仍以默认造型、空描述存在，任务标警告，用户可重跑补充；后面的「资产提示词」步骤照常运行（我方决定，不让补充失败卡住拆解）。

**不变的**：拆解后锁定所选集；分批并行和检查点机制；资产提示词步骤。

**要改的**：`drama_breakdown.go` 的流程、`breakdown_draft.md` / `breakdown_format.md` 改写为「造型与描述补充」提示词（`prompts/NOTICE.md` 同步更新）、积分估算。

- 正文按剧本行业版式排：角色名居中、对白缩进、括号再缩进、动作通栏、转场右对齐。
- 版面用「稿纸」方案（2026-11-25 用户从三版原型 `剧本编辑器-三版原型.html` 里选定；11-26 按 reveric 的剧本编辑器调整）：宋体正文、行高 2.05，左对齐——动作前悬挂 △，角色名加粗带冒号，括号灰色缩进，对白缩进并带 └ 引线，转场靠右，字幕居中加粗；场次标题下一行是只读的「出场人物」。编辑区上方是一行元素类型条（图标在上、文字在下：场次、动作、角色、括号、对白、转场、字幕、空镜、备注、闪回、闪回结束），光标所在行的类型高亮，不合法的置灰（原因在悬停提示里）；光标所在行左侧有一根细的定位线。场次标题的时间、内外景、地点点开是半透明弹层（不加说明小字，遵守 `web/docs/coding-standards.md` 6.2）。
- 视觉沿用「清透」胶囊风格（同上 6.1）。

### 8.2 键盘

| 操作 | 行为 |
| --- | --- |
| Enter | 在行尾新起一行，类型按规则：`character`/`parenthetical` → `dialogue`；`dialogue` → `action`；其他 → 同类型（`action` 接 `action`） |
| Tab / Shift+Tab | 在当前行循环切换类型，跳过不合法的类型（我方决定，同主流剧本软件；离开编辑区用 Esc） |
| 空行上按 Enter | 同样新起一行，不切换类型（2026-11-25 用户决定：回车就是换行，切类型只用 Tab 和上方类型条） |
| 行首 Backspace | 空行删除；非空行与上一行合并（类型不同时保留上一行类型） |
| `Mod+Enter` | 新建一场 |
| 粘贴多行纯文本 | 调 `/script/parse`，结果插到光标处；单行粘贴直接作为文本 |

- 实现基于现有 Tiptap：每种元素一个块级节点，场次标题一个带属性的节点（我方决定，沿用仓库已有依赖，不引入新编辑器库）。
- 输入法组字期间不触发 Enter / Tab 规则。

### 8.3 角色行与场次标题

- 角色行是一个下拉选择：输入时按人物表名字和别名模糊匹配；没有匹配时显示「新建人物：X」。选中后元素存 `character_id`，显示正式名。
- 角色行右侧可选 `OS` / `VO`。
- 场次标题由三个控件组成：内 / 外 / 内外，日 / 夜 / 自由文本，地点（地点表下拉，同样支持新建）。
- 人物或地点改名后，正文里所有引用即时显示新名。

### 8.4 场次栏与集统计（第③步）

- 场次栏列出本集各场：场号、短标题、情绪标签、出场人物头像（有 `canvas_node_id` 时用节点主图，否则用名字首字）。点击滚动到该场；可拖动调整场次顺序。
- 场次的短标题、梗概、情绪在场次栏里就地编辑；B（跨集状态提取）上线后会自动填写，本期只做手动。
- 集统计条：场次数、字数（不含 `note`）、对白占比、预估时长 vs 项目单集目标（`drama_projects.episode_seconds`）。预估公式（默认值，实现时用几集真实剧本校准）：对白按每秒 4 个汉字，动作每条 2 秒，空镜 / 字幕每条 2 秒。
- 人物区：本集出场人物及台词条数；点人物高亮其全部台词。

### 8.5 原著对照（第④步）

- 正文上方「原著对照」开关，打开后左右分栏：左侧只读显示这一集对应的原文单元 `unit_from..unit_to`（逐个调用 `GET /dramas/:id/units/:no`），右侧是剧本。两栏各自滚动，不做段落级联动（默认值）。
- 集上 `unit_from = 0`（没有对应原文）时开关不显示。
- 分栏宽度可拖动，记在 `localStorage`（失败不影响使用）。

### 8.6 保存与冲突

- 停手 1.5 秒或失焦自动保存（沿用 `Autosaver`），保存整集。
- 409 冲突、67005 锁定、外部任务改写的处理沿用 `DocEditor` 现有逻辑：本地无未保存改动直接换新内容，有改动则提示「内容已在别处修改」。
- 撤销 / 重做：用编辑器自身历史；一次自动保存不清空历史。

## 10. 目标、非目标与反目标

- **目标**：见 §1。
- **非目标**：剧本版本历史与对比；多人协作；docx / pdf / Fountain 导入导出；分镜改为读结构（仍读渲染出的 `script_md`；拆解在第⑤步改为读结构）；Agent 元素级编辑工具；道具表；A、B、C 三项。
- **反目标**（做出来也算失败）：
  - 转换后丢台词、丢场次，或把说话人张冠李戴。
  - 打字手感比现在的 Markdown 编辑器更慢、更卡（一集 5,000 字以内输入无可感延迟）。
  - ①–④ 上线后，拆解、分镜、上集衔接的结果因改造发生变化（同一份剧本，渲染出的 `script_md` 应与转换前语义一致）。第⑤步有意改变拆解方式，不受此条约束。
  - 第⑤步后，拆出的角色或场景与人物表、地点表对不上（多出、缺少或同人异名）。

### 14.2 第 ②③④ 步（前端）：已实现，未提交

- **已实现**：
  - ②元素化编辑器：场次标题（时间、内外景、地点）、八类元素加闪回标记；Enter 按规则接下一种、Tab 循环切类型、空行 Enter 也是换行、Backspace 合并或删除、⌘/Ctrl+Enter 新建一场；角色行是人物选择（可搜索、可新建），OS/VO 标记；上方类型条里不合法的类型置灰并在悬停里写原因；多行粘贴走解析接口；整集自动保存，revision 冲突时「重新加载 / 覆盖」，保存前先做和后端一致的顺序校验，不合法时写明第几场第几行；人物与地点弹窗（确认、改名、删除、新增）。
  - ③集统计条（场次数、字数、预估时长对单集目标，超出标红）；场次栏（场号、短标题、出场人物头像，点开写短标题、梗概、情绪标签，拖动调整顺序）。
  - ④原著对照：右上角开关，打开后左边只读显示这一集对应的原文单元，和稿纸各自滚动。
- **与设计的出入**：
  - 编辑器没有用 Tiptap：一行就是一条结构化数据，不是富文本，用「每行一个可编辑块」更直接，也不用在 ProseMirror 里重写一遍场内顺序约束。
  - 原著对照的分栏宽度固定为 2:3，没做拖动调整和 `localStorage` 记忆（设计里写了，留作后续）。
  - 点人物高亮他全部台词没做（原型里有，设计文档没有写成要求）。
  - 人物表在弹窗里而不是右侧常驻面板，因为剧本页右侧栏只在宽屏才显示。
  - 保存剧本（PUT）和改钩子、悬念（PATCH）共用集级 revision：两边保存成功后都要把新 revision 告诉对方（自动保存新增了 `setRevision`），人物改名会让后端重渲染这一集，所以改名前先存好未保存的改动、改完再对齐 revision。
- **验证**：新增前端测试 —— 剧本接口映射与请求 8 个、编辑逻辑（约束、校验、Enter、Tab、Backspace、统计、序列化、调整顺序）20 个、自动保存 `setRevision` 1 个、编辑器集成测试 5 个（jsdom 挂真实 hook 和组件：渲染、Enter 加行并保存、请求体里已有行带 ID 新行为 null、没选人物时保存被拦、锁定只读、读取失败）；全量 `bun test` 0 失败（本机 bun 1.4.4 退出码为 1 的老问题仍在）；格式、类型、lint、构建都通过。
- **未做**：没有在真实浏览器里点过（项目约定不用浏览器自动化），视觉和手感需要打开页面确认，尤其是 contenteditable 在输入法组字、粘贴、光标跳转上的表现。
